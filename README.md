# Трекер Атомных Привычек

Этот проект представляет собой веб-приложение для отслеживания и формирования полезных привычек, 
вдохновленное книгой Джеймса Клира "Атомные привычки". 
Цель трекера – помочь пользователям приобретать новые полезные привычки и избавляться от вредных.

## Концепция

В основе приложения лежит модель привычки, описываемая формулой: "Я буду [ДЕЙСТВИЕ] в [ВРЕМЯ] в [МЕСТО]".

### Модель Привычки

*   **Пользователь:** Создатель привычки.
*   **Место:** Место выполнения привычки.
*   **Время:** Время выполнения привычки.
*   **Действие:** Само действие привычки.
*   **Признак приятной привычки (is_pleasant):** Флаг, указывающий, является ли привычка приятной (например, вознаграждением).
*   **Связанная привычка:** Ссылка на приятную привычку, которая служит вознаграждением (доступно только для полезных привычек).
*   **Периодичность:** Частота выполнения привычки (в днях, по умолчанию ежедневно).
*   **Вознаграждение:** Чем пользователь может себя вознаградить после выполнения (доступно только для полезных привычек).
*   **Время на выполнение:** Максимальное время, которое должно быть потрачено на выполнение привычки (не более 120 секунд).
*   **Признак публичности:** Флаг, определяющий доступность привычки другим пользователям.

### Типы привычек:

*   **Полезная привычка:** Основное действие, которое может сопровождаться вознаграждением или связанной приятной привычкой.
*   **Приятная привычка:** Способ вознаграждения, который не может иметь собственного вознаграждения или связанной привычки.

### Валидация:

1.  Нельзя одновременно указывать **вознаграждение** и **связанную привычку** для одной привычки.
2.  **Время на выполнение** должно быть ≤ 120 секунд.
3.  **Связанные привычки** могут быть только типа "приятная".
4.  **Приятные привычки** не могут иметь **вознаграждение** или **связанную привычку**.
5.  **Периодичность** должна быть ≥ 1 раза в 7 дней (то есть, минимум раз в неделю).

### Пагинация:

*   Вывод списка привычек осуществляется по 5 элементов на страницу.

### Права доступа:

*   **CRUD операции** (Создание, Чтение, Обновление, Удаление) доступны только для собственных привычек пользователя.
*   **Просмотр публичных привычек** доступен всем пользователям без возможности редактирования.

## Интеграции:

*   **Telegram-бот:** Для отправки напоминаний о выполнении привычек.
*   **Celery:** Для обработки отложенных задач (например, отправка напоминаний, обработка периодических проверок).
*   **CORS:** Для обеспечения возможности взаимодействия фронтенда с API.
*   **Автодокументация API:** Генерация документации (например, с использованием Swagger/OpenAPI).

## Технологический Стек:

*   **Backend:** Python (Django REST Framework)
*   **База данных:** PostgreSQL (предпочтительно)
*   **Кэширование:** Redis
*   **Очередь задач:** Celery с Redis/RabbitMQ
*   **Управление зависимостями:** Poetry
*   **API документирование:** drf-spectacular (Swagger/OpenAPI)

## Тестирование:

В данном проекте уделяется особое внимание качеству кода и надежности функционала. 
**Покрытие тестами составляет более 80%**. 
Это достигается за счет использования комплексных юнит- и интеграционных тестов, охватывающих:

*   **Модели данных:** Проверка корректности создания, валидации и сохранения объектов привычек, пользователей и других сущностей.
*   **API эндпоинты:** Тестирование всех CRUD операций, авторизации, пагинации, обработки ошибок и прав доступа.
*   **Бизнес-логику:** Проверка корректной работы логики, связанной с типами привычек, валидационными правилами и взаимодействием между компонентами.
*   **Celery задачи:** Тестирование отправки уведомлений и других фоновых процессов.

Использование тестов гарантирует, что новые изменения не нарушают существующий функционал и обеспечивают стабильную работу приложения.

## Установка и Запуск:

Данный проект использует pip для управления зависимостями.

1.  Клонируйте репозиторий:
    ```bash
    git clone git@github.com:ann-novikova/HabApp.git
    cd HabApp
    ```
2.  Создайте и активируйте виртуальное окружение:
    ```bash
    python -m venv venv
    source venv/bin/activate  # Для Linux/macOS
    # venv\Scripts\activate  # Для Windows
    ```
3.  Установите зависимости с помощью pip:
    ```bash
    pip install -r requirements.txt
    ```
4.  Настройте переменные окружения. Рекомендуется использовать файл `.env` и установить переменную `DJANGO_SETTINGS_MODULE` в соответствии с вашим файловым путем.
5.  Примените миграции базы данных:
    ```bash
    python manage.py migrate
    ```
6.  Запустите сервер разработки Django:
    ```bash
    python manage.py runserver
    ```
7.  Для работы напоминаний и отложенных задач, запустите Celery worker:
    ```bash
    # Убедитесь, что Redis или RabbitMQ запущены
    celery -A config worker -l info --pool=sol
    ```
8.  Для запуска всех тестов:
    ```bash
    python manage.py test
    ```

## 9. Настройка удаленного сервера и деплоя

▌1. Предварительные Требования

Перед началом развертывания убедитесь, что у вас есть:

•  Удаленный сервер (VM): Настроенный и доступный по SSH. Рекомендуется использование облачных провайдеров, таких как Яндекс.Облако.
•  Docker: Установленный на удаленном сервере.
•  Git: Установленный на удаленном сервере.
•  GitHub Аккаунт: С настроенным репозиторием для вашего проекта.
•  Docker Hub Аккаунт: Для хранения Docker-образов.
•  SSH Ключ: Пара публичного/приватного ключей для безопасного доступа к серверу.

▌2. Настройка Удаленного Сервера

▌2.1. Обновление Системы и Установка Docker

1. Подключитесь к вашему серверу по SSH:
`ssh ваш_пользователь@IP_АДРЕС_СЕРВЕРА`
2. Обновите список пакетов и установленные пакеты:
`sudo apt update && sudo apt upgrade -y`
 
2.2. Настройка SSH для CI/CD
1. Скопируйте ваш публичный SSH ключ на сервер:
  Убедитесь, что ваш публичный ключ (например, ~/.ssh/id_rsa.pub) добавлен в файл ~/.ssh/authorized_keys на удаленном сервере.

3. Настройка GitHub Secrets
Для безопасной передачи чувствительных данных в CI/CD пайплайн, настройте следующие секреты в вашем GitHub репозитории (Settings -> Secrets and variables -> Actions):

•  SSH_KEY: Ваш приватный SSH ключ (без пароля, если он есть).
•  SSH_USER: Имя пользователя для SSH доступа к серверу.
•  SERVER_IP: Публичный IP-адрес вашего удаленного сервера.
•  DOCKER_HUB_USERNAME: Ваш логин в Docker Hub.
•  DOCKER_HUB_ACCESS_TOKEN: Ваш токен доступа к Docker Hub.
•  SECRET_KEY: Секретный ключ Django вашего приложения.
•  DATABASE_NAME: Имя вашей PostgreSQL базы данных.
•  DATABASE_USER: Пользователь PostgreSQL.
•  DATABASE_PASSWORD: Пароль пользователя PostgreSQL.
•  DATABASE_HOST: Хост для подключения к базе данных (обычно db если база в Docker Compose, или IP-адрес сервера).
•  DATABASE_PORT: Порт PostgreSQL (обычно 5432).

4.  GitHub Actions Workflow
Рабочий процесс CI/CD определен в файле .github/workflows/ci.yml.

4.1. Описание Workflow

Workflow состоит из трех основных этапов (jobs):

1. test:
  •  Запускает PostgreSQL в Docker-контейнере для тестов.
  •  Устанавливает зависимости Python.
  •  Выполняет миграции базы данных.
  •  Запускает Django тесты.
  •  Важно: Для этого шага используются переменные окружения, которые могут отличаться от продакшена (например, DATABASE_HOST может быть localhost или db в зависимости от того, как настроен сервис Postgres в GitHub Actions).

2. build:
  •  Подключается к Docker Hub.
  •  Собирает Docker-образ вашего приложения с использованием тега, соответствующего хешу коммита (${{ github.sha }}).
  •  Пушит собранный образ в Docker Hub.

3. deploy:
  •  Использует webfactory/ssh-agent для безопасного подключения к вашему удаленному серверу.
  •  Подтягивает последний Docker-образ из Docker Hub.
  •  Останавливает и удаляет предыдущий контейнер с именем myapp.
  •  Запускает новый контейнер myapp, пробрасывая порт 80 хоста на порт 8000 контейнера (-p 80:8000).
  •  Важно: Все необходимые переменные окружения (SECRET_KEY, DATABASE_HOST, ALLOWED_HOSTS и т.д.) должны быть переданы в docker run команду через -e флаг. 
В текущем примере они передаются через SSH, но в реальной ситуации их лучше передавать напрямую в docker run команду.

▌4.2. Запуск Workflow

•  Автоматический запуск: Workflow автоматически запускается при каждом push или pull_request в репозиторий.
•  Деплой: Для деплоя на продакшн, вам нужно будет вручную инициировать workflow (например, создав тег или изменив ветку), либо настроить его на автоматический деплой при слиянии в определенную ветку (например, main или production).
•  Локальная проверка: Перед пушем на GitHub, рекомендуется локально протестировать Docker-образ с помощью docker-compose.

▌5. Деплой на Сервер

После того, как GitHub Actions успешно прошел этапы test и build, этап deploy попытается развернуть приложение на вашем сервере.

1. Подключитесь к серверу по SSH.
2. Проверьте статус контейнера:
`docker ps`
Вы должны увидеть контейнер myapp, работающий, и порт 80 проброшенный на 8000.
3. Проверьте логи контейнера:
`docker logs myapp`
Ищите ошибки, связанные с подключением к базе данных, Celery, или Django.
4. Проверьте доступность приложения:
  Откройте в браузере http://IP_АДРЕС_СЕРВЕРА.
  •  Если вы получаете 404 на корневом URL, это означает, что маршрут / не настроен в urls.py. Исправьте urls.py и перезапустите контейнер (или пересоберите образ и запустите новый workflow деплоя).
  •  Если приложение не отвечает, проверьте:
    *  Правильность передачи переменных окружения в docker run (особенно ALLOWED_HOSTS и SECRET_KEY).
    *  Настройки базы данных (DATABASE_HOST, DATABASE_NAME, DATABASE_USER, DATABASE_PASSWORD). Убедитесь, что PostgreSQL на сервере настроен на прием внешних подключений.
    *  Настройки фаервола на сервере (порт 80 должен быть открыт).
